# dsh-ui-tidy 优化路线：从「我给自己的深度定制」到「别人也装得上、用得顺」

> 写于 0.4.7。目的只有一个：让没参与过这段开发的人，也能在没人指导下装上、看懂、出错自己救回来。
> 结论先行：**这个插件现在最大的问题不是功能不够，而是「装不上 / 坏了只能找我」。** 功能已经足够多了，再加功能只会让门槛更高。

---

## 一、现在挡住「更多人」的四道门槛

这四条不是猜的，是这次改造里真实撞过的坑。

| 门槛 | 现状 | 真实代价 |
| --- | --- | --- |
| **装** | 要懂 DSH profile：改 `~/.dsh/profiles/desktop/package.json` 的 `dependencies` + `dsh.profile.bundles` 两处，再重启 | 不熟这套结构的人在这里就停了；改错一个字段会连累整个 profile |
| **改** | 改一行 `client.js` 必须重启宿主，刷新页面只会卡在 Loading plugins（rev 变更后旧 bundle 取不到） | 开发者自己一轮改动要等 20–60 秒；用户完全无法参与 |
| **坏** | 出错时插件静默消失（顶栏没了），日志散在 `%APPDATA%\...\logs\crash-*.log`，界面上没有任何提示 | 用户唯一能做的就是「重置配置」或来找我。这次官方壳起不来，就是这么被误判成「插件把系统搞坏了」 |
| **懂** | 顶栏一排图标 + 自定义入口 + 「记忆」「M.O. · 工作流」「子代理」，术语密度高，没有首次使用说明 | 新人不知道怎么用，也不知道能关掉什么 |

**判断：优化重心应该从「加功能」转到「降低这四道门槛」。**

## 二、优化清单

### 第 1 层：装得上（收益最大，成本最低）

| 项 | 做法 | 状态 |
| --- | --- | --- |
| 一键注册 | `scripts/install.ps1`：自动定位 profile、备份 `package.json`、写入依赖与 bundle、提示「重启才生效」；`-Mode npm` 走 npm 包，`-Mode link` 走本地 checkout；`-DryRun` 只看不动 | ✅ 本轮已做 |
| 一键撤销 | `scripts/uninstall.ps1`：只删依赖与 bundle 两个字段，不碰 `cordis.patch.yml`、不碰用户设置、不碰会话 | ✅ 本轮已做 |
| 安装自检 | 安装后跑一次检查：用 `node --check` + 启动冒烟确认这份代码能装进当前宿主，而不是重启后才发现进不去 | ✅ 默认执行，失败不写盘（`-SkipVerify` 可跳过） |
| 发布到 npm | 现在只能 `link:`，官方市场按 npm 源装不到；发一次 npm 之后，安装就能缩减成 `pnpm add dsh-ui-tidy` + 加一行 bundle | ⬜ 需要 npm 账号 |

### 第 2 层：用得顺（减少「必须重启」与「必须找我」）

| 项 | 做法 | 状态 |
| --- | --- | --- |
| 出错不拖垮启动 | `exports.apply` 外层套 try/catch：某个 seat 抛异常只记一条 `console.error`，条目不激活但整壳继续跑 | ✅ 本轮已做 |
| 一键诊断 | 设置页「诊断」块：宿主席位命中、选择器命中、页面发现数、存储版本，一键复制 JSON。用户报障从「它不工作了」变成一段可读的读数 | ✅ 0.4.2 起 |
| 设置级回滚 | 设置页「备份与恢复」：导出/导入/恢复默认；代码级回滚交给 git | ✅ 0.4.5 起 |
| 热加载 | 宿主内建 `clientModules.rebuilt()`，前提是装 `@deepseek-ai/dsh-hmr`。装上后改代码不用重启 | ⬜ 需要你决定装不装（会增加一个宿主插件） |
| 首次使用引导 | 第一次激活时在顶栏旁给一条可关闭的提示：「这里是替代左侧栏的入口，右键/拖拽可以排序」 | ⬜ 待做（半天） |

### 第 3 层：坏了能自己救（信任门槛）

| 项 | 做法 | 状态 |
| --- | --- | --- |
| 失败自降级 | 连续两次激活失败就自动降级到 minimal（保留顶栏、不再接管左侧栏）并在控制台说明原因 | ✅ 0.4.8 |
| 安全模式 | 地址栏 `?uidy=off` / `?uidy=minimal` / `?uidy=on`，或 localStorage 同名开关 | ✅ 0.4.8 |
| 崩溃一键复原 | 安装时留一份 profile `package.json` 快照，出问题一键还原 | 部分（install.ps1 已备份，缺还原命令） |

### 第 4 层：传得开（可分享，不是必需）

- 英文文案补齐（目前设置页与诊断块中英混排）；深浅色两套截图；窄窗口（<1100px）下的折叠规则要在 README 写明；键盘可达（Tab / Esc 关闭弹层）。
- 一段 20 秒 GIF：左栏消失 → 顶栏图标 → 拖拽排序 → 会话弹层。比任何文字都省解释成本。

## 三、明确不做，以及为什么

| 想法 | 为什么不做 |
| --- | --- |
| 拆成多个包 / 多子代理并发写 | 宿主按单个 bundle 装载，拆包需要宿主加载约定支持；并发写同一批文件只会增加冲突，对维护是负资产 |
| 自建热更新服务器 | 宿主已经用 `clientModules` 掌管 bundle 图，外面再起一套必然打架 |
| 继续加功能（更多面板、更多开关） | 每多一个入口，新人的理解成本就多一分；当前功能已经超过「日常够用」的线 |
| 深度主题系统（配色、圆角、动效全套可调） | 维护成本高、收益低；真要个性化，直接改 `CUSTOM_CSS` 一段更省事 |

## 四、验收标准（怎么算「更适合更多人」）

1. 一个没看过代码的人，按 README 三条命令能装上，并在重启后看到顶栏 —— 不需要改任何 JSON。
2. 插件自身出错时，界面仍然可用，设置页能看到「上次激活失败」的诊断记录。
3. 用户不需要来找我，就能：复制诊断、恢复默认设置、卸载干净。
4. 代码侧：每次改动 `node --check` + `smoke/smoke-boot.mjs` 必过，`CHANGELOG.md` 有对应条目。

---

## 五、建议的下一步顺序

1. **装得上收尾**（半天）：`-Verify` 自检 + install 备份的还原命令。
2. **坏了能自己救**（一天）：安全模式开关 + 连续失败自杀 + 设置页显示上次失败原因。
3. **热加载决策**（十分钟确认 + 一次重启）：决定是否装 `@deepseek-ai/dsh-hmr`，装了之后我这边迭代不再占用你的重启次数。
4. **传得开**（半天）：README 三条命令 + GIF + 中英文案统一。

前两项做完，这个插件就从「作者自用」变成「别人敢装」；第三项做完，是「敢改」。
